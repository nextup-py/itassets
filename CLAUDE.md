# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

ITAssets — a Laravel 13 + Filament 5 admin panel for managing an organization's IT asset lifecycle (acquisition, assignment, maintenance, decommission). Livewire 4 + Tailwind CSS 4 + Vite. PHP 8.3+, MySQL in dev, SQLite in-memory in tests.

For the *why* behind design decisions (not just the *what*), see [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) — it covers the request lifecycle, the permissions/RoleSeeder deploy gotcha, the notification dual-write, and several real bugs (with root causes) this repo has already hit.

## Testing

- **Pest**, not PHPUnit syntax. Feature tests use `RefreshDatabase` (`tests/Pest.php:17`).
- Helpers in `tests/Pest.php`: `loginAsAdmin()`, `loginAsEditor()`, `loginAsViewer()`, `makeAdminUser()`, etc. They call `createRolesAndPermissions()` which builds roles/permissions programmatically — no DB seed needed for tests.
- `UserFactory` has states: `admin()`, `editor()`, `viewer()` (assign roles after `create()`).
- Tests run with SQLite `:memory:`, queue=sync, cache=array, session=array.

## Architecture

- **Single-panel Filament app**: `app/Providers/Filament/AdminPanelProvider.php`. The panel is served from the root path (`->path('')`, `->id('admin')` unchanged — the panel *ID* stays `admin` for named routes/`Filament::getLoginUrl()`/etc., only the URL prefix moved), not `/admin` as in a typical fresh Filament install. `routes/web.php` redirects any `/admin/...` request to the equivalent path without the prefix, so old bookmarks/links keep working. **Gotcha**: don't hardcode `/admin/...` in a URL string anywhere (mail action links, tests, docs) — use `Resource::getUrl(...)` / named routes instead, which resolve via the panel ID and stay correct regardless of `path()`; this is exactly the bug the panel-root migration had to fix in four `app/Notifications/*.php` classes that had `url("/admin/assets/{$id}")`-style hardcoded links.
- **Filament resources** live under `app/Filament/Resources/{Resource}/` with nested `Tables/`, `Schemas/`, `Pages/`, `RelationManagers/` subdirectories. Resources: AssetCategories, Assets, Assignments, Departments, Employees, Licenses, Locations, MaintenanceRecords, Suppliers, Supplies, Users.
- **Table conventions**: `SelectFilter`s on a `belongsTo`/`belongsToMany` column always use `->relationship('relationName', 'displayColumn')->searchable()->preload()` — never `->options(Model::pluck('name', 'id'))` (loads every row into memory on every table render regardless of whether the filter is used). `->options()` is reserved for enum-like fixed-value filters backed by a `public const` map (e.g. `Asset::STATUSES`, `License::TYPES`). Free-text identifier columns (person/asset names, tags) get both `->searchable()` and `->sortable()` for consistency with equivalent columns elsewhere in the table. Table `recordActions()` deliberately exclude `EditAction`/`DeleteAction` — every resource's `EditRecord` page already carries both as header actions (`getHeaderActions()`), so editing/deleting a row is a deliberate two-step (open View → header action), not a stray click in a dense table. `recordActions()` also excludes `ViewAction` itself: Filament's `ListRecords` gives every table a default `->recordUrl()` that, with no `view`/`edit` action registered, falls back to the resource's own View page (gated by `Resource::canView()`) — so clicking anywhere on a row already navigates to View with no button needed, and `recordActions()` is reserved for quick-transition row actions only (see below), or omitted entirely (`->recordActions([...])` call removed) when a resource has none. `toolbarActions()` likewise has no `DeleteBulkAction` — omit the whole `->toolbarActions([...])` call for a resource with no other bulk action, rather than leaving an empty `BulkActionGroup`. A handful of tables add a quick row `Action` for a single-field status transition that doesn't need the full edit form (e.g. Assets' `changeStatus`, Assignments' `returnNow`, Employees' `toggleActive`, Licenses' `renew`, MaintenanceRecords' `complete`, Supplies' `manualAdjustment`) — each is gated with `->authorize('update_{resource}')`, uses `->visible()` to hide when the transition doesn't apply, and either does a plain `->update()` (when a model `booted()` hook already handles the side effects, e.g. `Assignment`/`MaintenanceRecord`) or calls the same service a full-form action would (e.g. `SupplyAdjustmentService` for Supplies), never bypassing the business logic that keeps related records in sync. Notably, Assets' `changeStatus` is restricted to `stock`/`available`/`retired`/`lost` — `assigned`/`maintenance` are deliberately excluded because those transitions must go through `AssignmentService`/`MaintenanceService` (via the dedicated actions on `ViewAsset`) to create the corresponding `Assignment`/`MaintenanceRecord` row.
- **Permissions**: Spatie `laravel-permission`. Resources use a `HasResourcePermissions` trait (`app/Filament/Concerns/HasResourcePermissions.php`) checking `{action}_{resource}` permissions, e.g. `view_any_{resource}`, `view_{resource}`, `create_{resource}`, `update_{resource}`, `delete_{resource}`, plus custom `import_asset` / `export_report`. The trait overrides Filament's `get{X}AuthorizationResponse()` methods (not the `canX()` convenience methods — those already delegate to the former, but overriding only `canX()` leaves the actual UI actions unprotected). RelationManagers can't use the same trait (Filament authorizes them via instance methods, not static ones) — they use the analogous `HasRelationManagerPermissions` trait (`app/Filament/Concerns/HasRelationManagerPermissions.php`) instead, implementing `getPermissionName()`. Three roles: **Admin** (full CRUD), **Editor** (CRUD except delete + import assets + export reports), **Viewer** (read-only). Permission rows + role assignments are generated by `database/seeders/RoleSeeder.php` from a shared `$resources` array (kept in sync with `tests/Pest.php`'s `createRolesAndPermissions()`). **Important**: the deploy pipeline only runs `php artisan migrate --force` — it never re-runs seeders (see CI/CD below) — so adding a new resource to that array does nothing in production on its own. Any PR that adds a new Filament resource must also ship a migration that calls `(new \Database\Seeders\RoleSeeder())->run()` (safe/idempotent) so the new `{action}_{resource}` permissions actually get created and synced onto Admin/Editor/Viewer; see `database/migrations/2026_07_24_150000_sync_department_permissions.php` for the pattern.
- **Users**: `is_active` boolean gates panel access (`canAccessPanel()`); there is no hard delete from the UI — `EditUser`'s header action toggles `is_active` instead (guards: can't deactivate yourself, can't deactivate the last active Admin). `last_login_at` is tracked via an `Illuminate\Auth\Events\Login` listener. Panel has `->passwordReset()` + `->profile()` enabled for self-service. Only Admins can change a user's roles (the roles field is disabled for others), and an Editor/non-Admin can never grant or revoke the Admin role via the edit form even if submitted.
- **"Administración" is Admin-only**: the whole nav group (Users + the Roles/Permissions screens from `Althinect\FilamentSpatieRolesPermissionsPlugin`) is hidden from and unreachable by Editor/Viewer, on top of their ordinary `{action}_user` permission checks. `UserResource` overrides `authorizeAbility()` (from `HasResourcePermissions`) to additionally require `Auth::user()->hasRole('Admin')`. The Roles/Permissions screens ship from the plugin with **no authorization of their own** — Filament falls back to "open to any panel user" when no policy is registered for the underlying model — so `app/Policies/RolePolicy.php` and `PermissionPolicy.php` are registered for Spatie's `Role`/`Permission` models in `AppServiceProvider::boot()` (`Gate::policy(...)`, since those models live outside `app/Models` and aren't auto-discovered) and gate every ability to Admins only.
- **RelationManager row actions**: whether a row shows an inline `EditAction` or a "Ver" link-out depends on whether the related model has its own top-level Filament resource. `App\Filament\Resources\Shared\AssetsRelationManager` (an abstract base subclassed by `AssetCategories`/`Locations`/`Suppliers` — differing only in which of category/location it shows as the non-redundant 4th column, since the owner already implies the other one) and the `Assignments`/`MaintenanceRecords` relation managers on `Assets`/`Licenses` all link out to the related record's own View page (`AssetResource`/`AssignmentResource`/`MaintenanceRecordResource` `getUrl('view', ...)`) rather than editing inline, since `Assignment`/`MaintenanceRecord` are full resources with their own `EditRecord` page. `Licenses\AssignmentsRelationManager` (managing `LicenseAssignment`, which has no resource of its own — only relation-manager tabs on Licenses/Employees) keeps its `EditAction` inline, since there's no other page to link to. Form `Select`s inside relation managers use `->relationship()->searchable()->preload()` (with `modifyQueryUsing` for scoped options like "active employees, plus whoever's currently selected") the same as table `SelectFilter`s — not manual `Model::pluck()`.
- **Employees**: `is_active` boolean (not a `status` string). `legajo`, `document_number`, `email`, `position`, and `department_id` are all `NOT NULL`; `email`/`document_number`/`legajo` are unique. `department_id` is a FK to the `Departments` catalog resource (`restrictOnDelete()` — a department with employees can't be deleted). `document_type` is a separate, optional, nullable field (no NOT NULL/backfill needed, unlike the fields above) describing what kind of document `document_number` is — its fixed option set lives in `Employee::DOCUMENT_TYPES`, following the same `public const` pattern as `Asset::STATUSES` rather than a PHP enum (this codebase doesn't use native enums anywhere).
- **Audit**: Spatie `laravel-activitylog`, wired via `CausesActivity` (on `User`) + `LogsActivity` (on models) traits. Resources expose it as a read-only "Registro de auditoría" relation-manager tab via the shared `App\Filament\Resources\Shared\ActivityRelationManager` (reused across resources rather than duplicated per-resource).
- **Queue**: `database` driver (sync in tests); worker runs via `composer run dev`.
- **Cache/Session**: `database` driver in dev, `array` in tests.
- **Scheduler** (`routes/console.php`): `notifications:check` runs daily at 08:00, with `->timezone(fn () => Setting::get('timezone', config('app.timezone')))` so the hour follows the configurable installation timezone (see Settings pages below), not hardcoded UTC.
- **Notifications**: `WarrantyExpiryNotification`, `LicenseExpiryNotification`, `MaintenanceAlertNotification`, `AssetAssignmentNotification` (all `app/Notifications/`) implement `ShouldQueue` and use the `SendsToManagers` trait (`app/Notifications/Concerns/SendsToManagers.php`). `sendToManager(User $manager)` does a **dual-write**: `$manager->notify($this)` (mail + database channels) plus `$this->toFilament()->sendToDatabase($manager)` — the second write is required because Filament's in-panel notification bell (`->databaseNotifications()` on the panel, see below) only reads `notifications` rows where `data->format === 'filament'`, which plain Laravel notifications never produce on their own. Recipients are looked up via `User::scopeManagers()` (`role(['Admin', 'Editor'])`). Triggered from model events (`AssignmentAsset::created`, `Assignment::updated` on `returned_at`, `MaintenanceRecord::created`) and from `CheckExpirations` (warranty/license/maintenance-prolonged checks). `CheckExpirations::recentlyNotified()` dedupes with a 7-day cooldown (`COOLDOWN_DAYS`), querying `data->{key}` (e.g. `data->asset_id`) so the same entity/admin pair isn't renotified daily while still in its expiry window. `AssignmentDocumentNotification` is separate from the manager-facing notifications above: it goes to the **Employee** (not a manager), mail-only, attaching the same `pdf.assignment` view as a PDF (`Employee` uses the `Notifiable` trait so it can receive it, mail auto-routed via its existing `email` column). Gated by the `notify_employee_on_assignment` Setting (toggle in `GeneralSettings` → Notificaciones, default on) and centralized in `AssignmentService::notifyEmployee()`, called from all three places a new `Assignment` gets created with its assets already attached (`CreateAssignment::afterCreate()`, the Assets `AssignmentsRelationManager`'s `CreateAction ->after()`, and `AssignmentService::assign()` itself) — deliberately not hooked on `Assignment::created`, since the assets pivot rows haven't been attached yet at that point in any of these flows.
- **Services**: `AssignmentService`, `MaintenanceService`, `SupplyMovementService`, `SupplyAdjustmentService` hold business logic for assignment/maintenance/inventory operations — keep this logic out of Filament resource/page classes.
- **Insumos (Supplies)**: `App\Models\Supply` is a countable-stock catalog item (`quantity_available` + `quantity_damaged`), independent of `Asset` (which models one physical unit per row with no quantity). `SupplyResource`'s `ViewSupply` page exposes two actions, both gated by `update_supply` and both going through a service so the stock math and the audit-trail row are created in one DB transaction:
  - **Registrar movimiento** (`SupplyMovementService::register()`) records a `SupplyMovement` (`entrega` or `reemplazo`) to an `Employee` or a `Department`. `entrega` only decrements the delivered supply's `quantity_available`. `reemplazo` also increments a `quantity_damaged` bucket — on the same supply by default, or on a different `received_supply_id` when the returned unit is a different SKU (e.g. delivering a working drive and receiving a dead one back).
  - **Baja manual** (`SupplyAdjustmentService::register()`) records a `SupplyAdjustment` (reason: `loss`/`damage`/`theft`/`other`) and decrements `quantity_available`. Every adjustment is Blameable (`created_by`) and timestamped, and is listed read-only via the supply's own "Bajas / Ajustes de inventario" relation manager — there's no edit/delete UI for it, since it's meant as an audit trail.
  Both services throw a `RuntimeException` (caught by the calling action, shown as a Filament notification) when the requested quantity exceeds `quantity_available`, rather than letting stock go negative.
- **Maintenance ↔ Supplies**: `MaintenanceRecord` and `Supply` are linked through a `maintenance_record_supply` pivot (`quantity_used`), exposed as the `SuppliesRelationManager` on `MaintenanceRecordResource` using Filament's `AttachAction`/`DetachAction` (not `CreateAction`, since the supply already exists — only the pivot's `quantity_used` is new data). The pivot model (`MaintenanceRecordSupply`) decrements `Supply::quantity_available` on attach and restores it on detach, mirroring `AssignmentAsset`'s status-flip pattern — and refuses (throws) an attach that would exceed available stock. `AttachAction`/`DetachAction` have no dedicated authorization-response hook wired up by `HasRelationManagerPermissions` (that trait only covers create/update/delete), so they're gated explicitly with `->authorize('update_supply')`, the same way `Assets\Pages\ViewAsset`'s custom actions are.
- **Currency**: `format_currency()` helper in `app/helpers.php` (autoloaded via composer `files`) formats amounts using PHP's `NumberFormatter` (ext-intl). Amounts are stored in the installation's `base_currency` `Setting`; `display_currency` + `exchange_rate` are optional and only apply a conversion when a secondary reporting currency differs from `base_currency`. `display_locale` controls symbol/number formatting. All configurable via the Filament `GeneralSettings` page ("Regional" section). `format_currency()` also takes an optional second `$currency` argument for **per-record currency** — `Asset`/`License` both have a nullable `currency` column (informational only, no exchange-rate conversion for arbitrary currencies since only the single base↔display rate exists). Null, or a value equal to `base_currency`, goes through the normal base→display conversion path unchanged; any other value is shown as-is in that currency. `AssetValueWidget` groups priced assets by `currency ?: base_currency` before summing — blind `sum('purchase_price')` across mixed currencies would silently produce a meaningless number, so the widget shows one blended total when everything shares a currency (the common case) and a per-currency breakdown once a second currency appears.
- **Date format**: `current_date_format()` / `current_datetime_format()` helpers in `app/helpers.php` read the `date_format` `Setting` (default `d/m/Y`, configurable in `GeneralSettings` → Regional as a `Select` of common presets, not free text — a garbage PHP `date()` format string would break every date render in the app). Every Filament `->date()`/`->dateTime()`/`->displayFormat()` call and every manual `->format('d/m/Y'[' H:i'])` call (notifications, exports, the assignment PDF) goes through these helpers instead of a hardcoded literal, so changing the setting takes effect everywhere at once. Because Filament resource `configure()` methods and Blade views are re-evaluated on every request, calling the helpers directly (no `Closure` wrapper needed) is enough for the value to stay current — unlike the scheduler's `->timezone(fn () => ...)` in `routes/console.php`, which needs a closure because it's evaluated once at process boot.
- **Create/Edit form conventions**: like infolists, every `*Form.php` with more than one `Section` calls `$schema->columns(1)` before `->components([...])` — `CreateRecord`/`EditRecord` apply the same implicit `->columns(2)` default as `ViewRecord` (see below) whenever the schema doesn't declare its own, which would otherwise pair Sections two-per-row. `Select`s on a `belongsTo` field use `->relationship('relationName', 'displayColumn')->searchable()->preload()`, matching the table-filter convention — plus `->createOptionForm(fn (Schema $schema) => CatalogForm::configure($schema))` reusing that catalog resource's own Form class (`AssetCategoryForm`/`LocationForm`/`SupplierForm`/`DepartmentForm`) so a missing category/location/supplier/department can be created inline via the Select's own "+" modal instead of abandoning the current form. This applies only to genuine catalog lookups; it's deliberately NOT used for `MaintenanceRecordForm`'s `asset_id` or `AssignmentForm`'s Repeater-nested `asset_id` (creating an `Asset` needs the full multi-section `AssetForm`, too heavy for an inline modal) or for `AssignmentForm`'s top-level `employee_id` beyond its own `->relationship()` conversion (same reasoning re: `EmployeeForm`). Some `relationship()` Selects need custom-scoped options (e.g. `AssignmentForm`'s `employee_id`: only active employees, plus whoever's already selected on this record) — done via `modifyQueryUsing: fn (Builder $query, ?Model $record) => ...`, the same pattern used in relation-manager forms.
- **Setting model**: key-value store — `App\Models\Setting::get($key, $default)` / `::set($key, $value)`.
- **View page infolists** (`app/Filament/Resources/*/Schemas/*Infolist.php`): every one calls `$schema->columns(1)` before `->components([...])`. Filament's `ViewRecord::defaultInfolist()` applies `->columns(2)` to the infolist automatically whenever the schema doesn't already declare its own columns (`hasCustomColumns()`) — without the explicit `->columns(1)` override, top-level `Section`s pair up two-per-row instead of stacking, which reads as an arbitrary/unbalanced layout once a resource has an odd number of sections. Multi-column layout still happens *inside* each `Section` via that section's own `->columns(N)`. Several infolists also surface a related-record count as a `TextEntry` computed via `->state(fn ($record) => $record->relation()->count())->badge()` (e.g. Employee's active assignments/license count, Department's employee count, Supplier's asset/license/maintenance counts) so a hub entity's scale is visible without switching to its relation-manager tab.
- **PDF**: Assignment PDFs via DomPDF at `GET /assignments/{assignment}/pdf` (`AssignmentPdfController::download`, `auth` middleware + `view_assignment` permission check — assignment IDs are sequential, so this can't be left open). `PdfSettings` (Filament page) controls the title/intro/clauses/closing text and an optional `company_logo` (embedded into the PDF as a base64 data URI, not a file path, since DomPDF has no local-file config published in this project). `resources/views/pdf/assignment.blade.php` accepts an optional `$overrides` array whose keys take precedence over the corresponding `Setting::get()` call — this is what `PdfSettings`' "Vista previa" action uses to render a sample PDF (fixture employee/asset, none of it persisted) from the form's current *unsaved* values: since a Livewire action closure can't return an HTTP response directly, the unsaved override data is stashed in cache under a short-lived random token (`AssignmentPdfController::preview`, `GET /assignments/pdf-preview/{token}`, same auth+role gate as the settings page) and opened via `$this->js('window.open(...)')`.
- **Asset QR codes**: `App\Support\AssetQrCode::dataUri(Asset $asset)` renders a QR (via `chillerlan/php-qrcode` — a transitive dependency of Filament's own 2FA feature, so no extra package was needed) encoding `GET /assets/{asset}/public` — a standalone, **unauthenticated** page (`AssetPublicController`, `resources/views/assets/public.blade.php`) showing only identification basics (code, name, category, brand/model, serial, status); it deliberately omits the current employee assignment (PII), which is only visible after clicking through to the real Filament View page (auth-gated as usual). The QR is shown on `ViewAsset`'s infolist (in the "Código QR" section, alongside a "Descargar QR"/"Imprimir etiqueta" pair added via that Section's own `->headerActions()` — Section-embedded actions aren't in the page's standard action registry, so they're tested via `assertSee`/`assertDontSee` on the button label, not `assertActionVisible`/`Hidden`) and printable in bulk via the Assets table's `printQrCodes` BulkAction (`export_report`-gated, Admin-only). Both are defined inside a **static** `configure()` method (`AssetsTable`/`AssetInfolist`), so `$this->js()` isn't available the way it is in an instance-method context (see `PdfSettings`' preview action above) — they use `->url(..., shouldOpenInNewTab: true)` instead. **Gotcha**: in production, `GET /assets/{asset}/qr-download` (raw PNG download) 404s from nginx itself if the route path ends in an image extension like `.png` — this project's nginx vhost has a `location ~* ^.+\.(...|png|...)$ { ... }` block with no `try_files` fallback to `index.php`, so any URL matching that regex is treated as a static-file lookup and never reaches PHP-FPM at all (a bare nginx 404, no Laravel trace). The route is named `qr-download`, not `qr.png`, specifically to avoid this — never give an app route a static-asset-looking extension. The bulk-print flow (selected asset IDs → cache token → `GET /assets/qr-sheet/{token}`, `AssetQrSheetController`, same auth+`export_report` gate, renders a 3-per-row label grid via `resources/views/pdf/qr-sheet.blade.php` with DomPDF) is unaffected since its URL has no such extension.
- **Mail**: notifications are `ShouldQueue` (see Notifications bullet), but *which* mailer actually sends them is decided at runtime, not just `.env`. `MailSettings` (Filament page, Admin-only) lets an admin pick `log`/`resend`/`smtp` and enter provider credentials, storing them via `Setting::set()` — the Resend API key and SMTP password are encrypted with `Crypt::encryptString()` before being stored (the `settings` table itself has no encryption of its own) and decrypted back only where needed. `App\Services\MailConfigService::apply()`, called from `AppServiceProvider::boot()` on every request, overwrites `config('mail.*')` with whatever's saved in Settings (falling back to untouched `.env`-based config when `mail_mailer` was never set) — guarded with a `Schema::hasTable('settings')` check so it can't break a pre-migration boot (e.g. the deploy's own `artisan migrate`). `MailSettings`' "Enviar correo de prueba" action applies the *unsaved* form state via the same override mechanism and sends `App\Mail\TestMail` (a real `Mailable`, not `Mail::raw()` — Laravel's `MailFake::raw()` is a no-op stub, so a raw/closure-based send is invisible to `Mail::fake()`/`assertSent()` in tests).
- **Custom action feedback**: every custom `Action`/`BulkAction` with an `->action()` closure (not `EditAction`/`CreateAction`/`DeleteAction`, which notify automatically) sends its own `Notification::make()->success()->title(...)->send()` on completion — a bare closure with no `Notification` call is genuinely silent, since Filament only auto-notifies for the built-in CRUD actions. Only `SupplyMovementService`/`SupplyAdjustmentService` (used by Supplies' actions) throw a domain `RuntimeException` for an expected business-rule violation (insufficient stock), so only those call sites wrap the service call in `try/catch (RuntimeException $e)` → `->danger()` notification with `$e->getMessage()`. `AssignmentService`/`MaintenanceService` (used by `ViewAsset`'s assign/return/sendToMaintenance/closeMaintenance) never throw, so they're deliberately left without a catch — wrapping a call that can't throw a known exception in a generic `try/catch` would just mask real bugs behind a vague message instead of surfacing them.
- **Import/Export**: Laravel Excel — `AssetImport`/`EmployeeImport`/`SupplyImport` (each implements `WithValidation` with a `rules()` method plus `SkipsOnFailure`/`SkipsOnError`, so bad rows are skipped and reported instead of aborting the whole import), `AssetsExport`/`EmployeesExport`/`SuppliesExport`, `AssignmentsExport`, `AssetTemplateExport`/`EmployeeTemplateExport`/`SupplyTemplateExport`. Each importer resolves free-text relation columns (category/supplier/location/department names) via `firstOrCreate`, upserts on the resource's natural business key (`asset_tag`/`legajo`/`name` respectively) via `WithUpserts`/`uniqueBy()`, and validates numeric-looking spreadsheet cells with a bare `'nullable'` rule instead of `'nullable|string'` — Laravel Excel hands typed cells to the validator (a purely-numeric ID like a document number parses as an int), so a `string` rule spuriously rejects valid rows; cast to string only inside `model()`. Each of the 3 resources' `ListRecords` page has a matching 3-button header-action group (`downloadTemplate`, `import{Resource}`, `export{Resource}`) gated by `import_{resource}`/`export_report` permissions (`export_report` is shared across all resources' exports, matching the Reports page; `import_*` is per-resource, added to `RoleSeeder::EXTRA_PERMISSIONS`).
- **Custom Filament pages** (`app/Filament/Pages/`): `GeneralSettings` (currency/exchange-rate/locale/timezone/date-format — `canAccess()` restricted to Admin/Editor), `PdfSettings` (assignment PDF title/intro/clauses/closing/logo, same `canAccess()` restriction, plus a "Vista previa" action — see PDF bullet below), `MailSettings` (mail provider — see Mail bullet below, `canAccess()` restricted to **Admin only**, stricter than the other Sistema pages since it touches credentials), `Reports` (asset/assignment export actions only — no `canAccess()` override, gated per-action by the `export_report` permission instead). **Gotcha**: any custom page with its own form needs its Blade view wrapped in `<x-filament::page><form wire:submit="save">{{ $this->form }}</form></x-filament::page>` — a bare `{{ $this->form }}` has no ancestor `<form>` (so the submit button does nothing) and no heading/breadcrumb chrome. This was a real production bug on `GeneralSettings`/`PdfSettings`; `Livewire::test()->call('save')`-style tests can't catch it since they invoke the method directly, so there's an HTTP-level regression test asserting `wire:submit="save"` is actually present in the rendered HTML. A schema-embedded `Actions::make([...])` button (the `save` action on every Sistema page, plus `PdfSettings`' `preview` and `MailSettings`' `sendTest`) isn't a resource/table action Filament's `callAction()` test helper recognizes — every one of them wraps a public page method (`->submit('save')` or `->action(fn () => $this->methodName())`) and gets tested via `Livewire::test()->call('methodName', ...)` directly instead.
- **Dashboard widgets** (`app/Filament/Widgets/`, auto-discovered): `AssetStatsWidget`/`AssetValueWidget` (stat cards), `AssetsByStatusChartWidget`/`AssetsByCategoryChartWidget` (charts), `WarrantyAlertsWidget` (warranties expiring within ±60 days), `RecentAssetsWidget` (last 5 assets), `ActiveMaintenanceWidget` (assets in maintenance), `RecentNotificationsWidget` (current user's recent notifications, with mark-as-read). **Gotchas**: (1) a widget query's `->limit(N)` is silently overridden by Filament's own table pagination (`forPage()` replaces rather than combines with an existing limit) — a widget needs `->paginated(false)` too if it must show a fixed "last N" regardless of total row count (see `RecentAssetsWidget`); (2) all widgets lazy-load via `x-intersect` (fire only once their placeholder scrolls into the viewport) — a widget that "renders blank" in a headless/short-viewport test is very likely just not scrolled into view yet, not broken.
- **Navigation groups**: `AdminPanelProvider::panel()` declares `->navigationGroups(['Inventario', 'Catálogos', 'Administración', 'Sistema'])` explicitly (so order isn't left to folder-discovery order). Inventario: Assets, Assignments, MaintenanceRecords, Licenses, Reports. Catálogos: AssetCategories, Locations, Suppliers, Departments, Employees. Administración: Users (+ Roles/Permissions from the `Althinect\FilamentSpatieRolesPermissionsPlugin` plugin). Sistema: GeneralSettings, PdfSettings, MailSettings.

## Conventions

- 4-space indent, LF line endings (`.editorconfig`).
- Vite entry points: `resources/css/app.css` + `resources/js/app.js`. Tailwind CSS 4 via `@tailwindcss/vite`.

## CI/CD

- `.github/workflows/tests.yml`: on push/PR to `main`, installs PHP 8.3 + Node 22 deps, builds assets, runs `composer run test`.
- `.github/workflows/deploy.yml`: on push to `main`, deploys via a reusable workflow (`nextup-py/deploy-actions`) — runs tests and migrations, then deploys over SSH. Requires `ITASSETS_*` secrets. **Does not run seeders** — `php artisan migrate --force` only. Any change that needs seeded/synced data in production (e.g. new permissions) must ship as a migration, not rely on a seeder class alone.
