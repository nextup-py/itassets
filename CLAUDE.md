# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

ITAssets — a Laravel 13 + Filament 5 admin panel for managing an organization's IT asset lifecycle (acquisition, assignment, maintenance, decommission). Livewire 4 + Tailwind CSS 4 + Vite. PHP 8.3+, MySQL in dev, SQLite in-memory in tests.

For the *why* behind design decisions (not just the *what*), see [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) — it covers the request lifecycle, the permissions/RoleSeeder deploy gotcha, the notification dual-write, and several real bugs (with root causes) this repo has already hit.

## Testing

- **Pest**, not PHPUnit syntax. Feature tests use `RefreshDatabase` (`tests/Pest.php:17`).
- Helpers in `tests/Pest.php`: `loginAsAdmin()`, `loginAsEditor()`, `loginAsViewer()`, `makeAdminUser()`, etc. They call `createRolesAndPermissions()` which builds roles/permissions programmatically — no DB seed needed for tests.
- `UserFactory` has states: `admin()`, `editor()`, `viewer()` (assign roles after `create()`).
- Tests run with SQLite `:memory:`, queue=sync, cache=array, session=array.

## Architecture

- **Single-panel Filament app**: `app/Providers/Filament/AdminPanelProvider.php`.
- **Filament resources** live under `app/Filament/Resources/{Resource}/` with nested `Tables/`, `Schemas/`, `Pages/`, `RelationManagers/` subdirectories. Resources: AssetCategories, Assets, Assignments, Departments, Employees, Licenses, Locations, MaintenanceRecords, Suppliers, Users.
- **Permissions**: Spatie `laravel-permission`. Resources use a `HasResourcePermissions` trait (`app/Filament/Concerns/HasResourcePermissions.php`) checking `{action}_{resource}` permissions, e.g. `view_any_{resource}`, `view_{resource}`, `create_{resource}`, `update_{resource}`, `delete_{resource}`, plus custom `import_asset` / `export_report`. The trait overrides Filament's `get{X}AuthorizationResponse()` methods (not the `canX()` convenience methods — those already delegate to the former, but overriding only `canX()` leaves the actual UI actions unprotected). RelationManagers can't use the same trait (Filament authorizes them via instance methods, not static ones) — they use the analogous `HasRelationManagerPermissions` trait (`app/Filament/Concerns/HasRelationManagerPermissions.php`) instead, implementing `getPermissionName()`. Three roles: **Admin** (full CRUD), **Editor** (CRUD except delete + import assets + export reports), **Viewer** (read-only). Permission rows + role assignments are generated by `database/seeders/RoleSeeder.php` from a shared `$resources` array (kept in sync with `tests/Pest.php`'s `createRolesAndPermissions()`). **Important**: the deploy pipeline only runs `php artisan migrate --force` — it never re-runs seeders (see CI/CD below) — so adding a new resource to that array does nothing in production on its own. Any PR that adds a new Filament resource must also ship a migration that calls `(new \Database\Seeders\RoleSeeder())->run()` (safe/idempotent) so the new `{action}_{resource}` permissions actually get created and synced onto Admin/Editor/Viewer; see `database/migrations/2026_07_24_150000_sync_department_permissions.php` for the pattern.
- **Users**: `is_active` boolean gates panel access (`canAccessPanel()`); there is no hard delete from the UI — `EditUser`'s header action toggles `is_active` instead (guards: can't deactivate yourself, can't deactivate the last active Admin). `last_login_at` is tracked via an `Illuminate\Auth\Events\Login` listener. Panel has `->passwordReset()` + `->profile()` enabled for self-service. Only Admins can change a user's roles (the roles field is disabled for others), and an Editor/non-Admin can never grant or revoke the Admin role via the edit form even if submitted.
- **Employees**: `is_active` boolean (not a `status` string). `legajo`, `document_number`, `email`, `position`, and `department_id` are all `NOT NULL`; `email`/`document_number`/`legajo` are unique. `department_id` is a FK to the `Departments` catalog resource (`restrictOnDelete()` — a department with employees can't be deleted). `document_type` is a separate, optional, nullable field (no NOT NULL/backfill needed, unlike the fields above) describing what kind of document `document_number` is — its fixed option set lives in `Employee::DOCUMENT_TYPES`, following the same `public const` pattern as `Asset::STATUSES` rather than a PHP enum (this codebase doesn't use native enums anywhere).
- **Audit**: Spatie `laravel-activitylog`, wired via `CausesActivity` (on `User`) + `LogsActivity` (on models) traits. Resources expose it as a read-only "Registro de auditoría" relation-manager tab via the shared `App\Filament\Resources\Shared\ActivityRelationManager` (reused across resources rather than duplicated per-resource).
- **Queue**: `database` driver (sync in tests); worker runs via `composer run dev`.
- **Cache/Session**: `database` driver in dev, `array` in tests.
- **Scheduler** (`routes/console.php`): `notifications:check` runs daily at 08:00, with `->timezone(fn () => Setting::get('timezone', config('app.timezone')))` so the hour follows the configurable installation timezone (see Settings pages below), not hardcoded UTC.
- **Notifications**: `WarrantyExpiryNotification`, `LicenseExpiryNotification`, `MaintenanceAlertNotification`, `AssetAssignmentNotification` (all `app/Notifications/`) implement `ShouldQueue` and use the `SendsToManagers` trait (`app/Notifications/Concerns/SendsToManagers.php`). `sendToManager(User $manager)` does a **dual-write**: `$manager->notify($this)` (mail + database channels) plus `$this->toFilament()->sendToDatabase($manager)` — the second write is required because Filament's in-panel notification bell (`->databaseNotifications()` on the panel, see below) only reads `notifications` rows where `data->format === 'filament'`, which plain Laravel notifications never produce on their own. Recipients are looked up via `User::scopeManagers()` (`role(['Admin', 'Editor'])`). Triggered from model events (`AssignmentAsset::created`, `Assignment::updated` on `returned_at`, `MaintenanceRecord::created`) and from `CheckExpirations` (warranty/license/maintenance-prolonged checks). `CheckExpirations::recentlyNotified()` dedupes with a 7-day cooldown (`COOLDOWN_DAYS`), querying `data->{key}` (e.g. `data->asset_id`) so the same entity/admin pair isn't renotified daily while still in its expiry window.
- **Services**: `AssignmentService`, `MaintenanceService` hold business logic for assignment/maintenance operations — keep this logic out of Filament resource/page classes.
- **Currency**: `format_currency()` helper in `app/helpers.php` (autoloaded via composer `files`) formats amounts using PHP's `NumberFormatter` (ext-intl). Amounts are stored in the installation's `base_currency` `Setting`; `display_currency` + `exchange_rate` are optional and only apply a conversion when a secondary reporting currency differs from `base_currency`. `display_locale` controls symbol/number formatting. All configurable via the Filament `GeneralSettings` page ("Regional" section). `format_currency()` also takes an optional second `$currency` argument for **per-record currency** — `Asset`/`License` both have a nullable `currency` column (informational only, no exchange-rate conversion for arbitrary currencies since only the single base↔display rate exists). Null, or a value equal to `base_currency`, goes through the normal base→display conversion path unchanged; any other value is shown as-is in that currency. `AssetValueWidget` groups priced assets by `currency ?: base_currency` before summing — blind `sum('purchase_price')` across mixed currencies would silently produce a meaningless number, so the widget shows one blended total when everything shares a currency (the common case) and a per-currency breakdown once a second currency appears.
- **Date format**: `current_date_format()` / `current_datetime_format()` helpers in `app/helpers.php` read the `date_format` `Setting` (default `d/m/Y`, configurable in `GeneralSettings` → Regional as a `Select` of common presets, not free text — a garbage PHP `date()` format string would break every date render in the app). Every Filament `->date()`/`->dateTime()`/`->displayFormat()` call and every manual `->format('d/m/Y'[' H:i'])` call (notifications, exports, the assignment PDF) goes through these helpers instead of a hardcoded literal, so changing the setting takes effect everywhere at once. Because Filament resource `configure()` methods and Blade views are re-evaluated on every request, calling the helpers directly (no `Closure` wrapper needed) is enough for the value to stay current — unlike the scheduler's `->timezone(fn () => ...)` in `routes/console.php`, which needs a closure because it's evaluated once at process boot.
- **Setting model**: key-value store — `App\Models\Setting::get($key, $default)` / `::set($key, $value)`.
- **PDF**: Assignment PDFs via DomPDF at `GET /assignments/{assignment}/pdf`. `PdfSettings` (Filament page) controls the intro/clauses/closing text and an optional `company_logo` (embedded into the PDF as a base64 data URI, not a file path, since DomPDF has no local-file config published in this project).
- **Import/Export**: Laravel Excel — `AssetImport` (implements `WithValidation` with a `rules()` method plus `SkipsOnFailure`/`SkipsOnError`, so bad rows are skipped and reported instead of aborting the whole import), `AssetsExport`, `AssignmentsExport`, `AssetTemplateExport`.
- **Custom Filament pages** (`app/Filament/Pages/`): `GeneralSettings` (currency/exchange-rate/locale/timezone/date-format — `canAccess()` restricted to Admin/Editor), `PdfSettings` (assignment PDF text + logo — same `canAccess()` restriction), `Reports` (asset/assignment export actions only — no `canAccess()` override, gated per-action by the `export_report` permission instead). **Gotcha**: any custom page with its own form needs its Blade view wrapped in `<x-filament::page><form wire:submit="save">{{ $this->form }}</form></x-filament::page>` — a bare `{{ $this->form }}` has no ancestor `<form>` (so the submit button does nothing) and no heading/breadcrumb chrome. This was a real production bug on `GeneralSettings`/`PdfSettings`; `Livewire::test()->call('save')`-style tests can't catch it since they invoke the method directly, so there's an HTTP-level regression test asserting `wire:submit="save"` is actually present in the rendered HTML.
- **Dashboard widgets** (`app/Filament/Widgets/`, auto-discovered): `AssetStatsWidget`/`AssetValueWidget` (stat cards), `AssetsByStatusChartWidget`/`AssetsByCategoryChartWidget` (charts), `WarrantyAlertsWidget` (warranties expiring within ±60 days), `RecentAssetsWidget` (last 5 assets), `ActiveMaintenanceWidget` (assets in maintenance), `RecentNotificationsWidget` (current user's recent notifications, with mark-as-read). **Gotchas**: (1) a widget query's `->limit(N)` is silently overridden by Filament's own table pagination (`forPage()` replaces rather than combines with an existing limit) — a widget needs `->paginated(false)` too if it must show a fixed "last N" regardless of total row count (see `RecentAssetsWidget`); (2) all widgets lazy-load via `x-intersect` (fire only once their placeholder scrolls into the viewport) — a widget that "renders blank" in a headless/short-viewport test is very likely just not scrolled into view yet, not broken.
- **Navigation groups**: `AdminPanelProvider::panel()` declares `->navigationGroups(['Inventario', 'Catálogos', 'Administración', 'Sistema'])` explicitly (so order isn't left to folder-discovery order). Inventario: Assets, Assignments, MaintenanceRecords, Licenses, Reports. Catálogos: AssetCategories, Locations, Suppliers, Departments, Employees. Administración: Users (+ Roles/Permissions from the `Althinect\FilamentSpatieRolesPermissionsPlugin` plugin). Sistema: GeneralSettings, PdfSettings.

## Conventions

- 4-space indent, LF line endings (`.editorconfig`).
- Vite entry points: `resources/css/app.css` + `resources/js/app.js`. Tailwind CSS 4 via `@tailwindcss/vite`.

## CI/CD

- `.github/workflows/tests.yml`: on push/PR to `main`, installs PHP 8.3 + Node 22 deps, builds assets, runs `composer run test`.
- `.github/workflows/deploy.yml`: on push to `main`, deploys via a reusable workflow (`nextup-py/deploy-actions`) — runs tests and migrations, then deploys over SSH. Requires `ITASSETS_*` secrets. **Does not run seeders** — `php artisan migrate --force` only. Any change that needs seeded/synced data in production (e.g. new permissions) must ship as a migration, not rely on a seeder class alone.
